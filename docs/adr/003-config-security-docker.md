# ADR 003: Конфигурация, проверки безопасности и оптимизация Docker

## Статус

Предложено — ожидает рассмотрения командой в Pull Request.

## Дата

2026-10-21

## Контекст

В приложении To-Do List API на FastAPI параметры подключения к PostgreSQL ранее читались непосредственно из переменных окружения. Документация FastAPI была доступна независимо от режима запуска. Dockerfile использовал одноэтапную сборку. Для практики №4 требуется централизовать настройки, добавить автоматические проверки безопасности и оптимизировать контейнер.

## Рассмотренные варианты

| Вопрос | Вариант A | Вариант B (выбран) |
|---|---|---|
| Конфигурация | Чтение `os.environ` в обработчиках | `pydantic-settings` и единый `config.py` |
| Документация API | Всегда доступна | Доступна только при `APP_ENV=dev` |
| Проверки | Ручная проверка перед коммитом | `pre-commit` и `detect-secrets` |
| Docker | Одноэтапный Dockerfile | Двухэтапная сборка с отдельной установкой зависимостей |

## Решение

1. Использовать `pydantic-settings` в `config.py`: `APP_ENV` принимает `dev` или `prod`, `DB_CONNECT_TIMEOUT` ограничен диапазоном 1–60 секунд, `DATABASE_URL` может отсутствовать вне Docker.
2. В `main.py` включать `/docs`, `/redoc` и `/openapi.json` только в режиме `dev`.
3. Хранить пример настроек в `.env.example`; локальный `.env` не добавлять в Git. В Docker Compose формировать `DATABASE_URL` из `POSTGRES_*` и передавать `APP_ENV`, `DB_CONNECT_TIMEOUT` в контейнер приложения.
4. Добавить `.pre-commit-config.yaml` с проверками пробелов, окончаний файлов, YAML, TOML, крупных файлов, приватных ключей и секретов. Использовать `.secrets.baseline` для `detect-secrets`.
5. Применить двухэтапный Dockerfile: зависимости устанавливаются в стадии `builder` с `--prefix=/install`, затем копируются в `runtime`. Приложение запускается от `appuser` (UID 10001), предусмотрен `HEALTHCHECK`.
6. Сохранить Poetry как менеджер зависимостей проекта; обновлять `pyproject.toml` и `poetry.lock` совместно, а `requirements.txt` экспортировать для Docker-сборки.

## Обоснование

Централизованная конфигурация упрощает проверку параметров. Отключение документации в production сокращает доступную поверхность API. Проверки до коммита снижают риск случайного добавления ключей и секретов. Двухэтапная сборка позволяет не переносить в итоговый образ промежуточные инструменты и файлы сборки.

## Проверка реализации

| Проверка | Полученный результат |
|---|---|
| `APP_ENV=dev`, запрос `/docs` | HTTP 200 |
| `APP_ENV=prod`, запрос `/docs` | HTTP 404 |
| Запрос `/health` с PostgreSQL | `healthy / ok` |
| `docker compose ps` | Оба сервиса `healthy` (проверено до последней оптимизации образа) |
| `docker compose exec app id` | `uid=10001(appuser)` (проверено до последней оптимизации образа) |
| `pre-commit run --all-files` | Все семь проверок `Passed` |
| Старый одноэтапный образ | 285 MB (`DISK USAGE`) |
| Первая двухэтапная версия | 305 MB (`DISK USAGE`) |
| Оптимизированный двухэтапный образ | 268 MB (`DISK USAGE`) |

Уменьшение относительно исходного образа: 17 MB, приблизительно 6%. После последней оптимизации Docker Compose был успешно пересобран и запущен; повторная проверка `id` и `/health` для финального образа рекомендуется перед PR.

## Последствия

### Положительные

- Настройки приложения сосредоточены в одном месте и валидируются.
- Документация API отключена в режиме `prod`.
- Автоматические проверки запускаются перед коммитом.
- Итоговый Docker-образ меньше исходного, а приложение настроено на запуск без прав root.

### Отрицательные и риски

- Разработчикам необходимо настроить `.env` и установить `pre-commit`.
- Автоматические исправления хуков могут затронуть файлы других практик: изменения нужно проверять перед коммитом.
- Базовый файл `detect-secrets` следует пересматривать: найденный секрет нельзя считать безопасным только потому, что он внесён в baseline.
- При изменении зависимостей необходимо повторно экспортировать `requirements.txt` из Poetry.
