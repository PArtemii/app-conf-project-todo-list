**Проект:** ИИ-Ассистент к To-Do List 

## Контекст
Необходимо реализовать интеграцию локального ИИ-агента с базой данных To-Do листа для фильтрации задач по приоритету. Главные ограничения проекта: работа локальной модели без доступа к сети Интернет (Ollama qwen3:4b-instruct), необходимость жесткой фильтрации параметров на входе и использование общего конфигурационного файла `.env` с параллельным курсом по бэкенд-разработке.

## Рассмотренные варианты
1. Конфигурация AI-слоя через стандартные системные вызовы `os.getenv()`.
2. Конфигурация через библиотеку `pydantic-settings` (Выбрано).
3. Проброс необработанных исключений (traceback) из кода инструмента наружу агенту.
4. Безопасный возврат ошибок ИИ-агенту через стандартизированную JSON-строку (Выбрано).

## Решение
Мы выбрали `pydantic-settings` для управления конфигурацией, так как это гарантирует строгую валидацию типов (например, через тип `Literal` для провайдера) еще на этапе запуска приложения и защищает проект от падений из-за опечаток в `.env`.

Для интеграции агента с To-Do листом разработан инструмент `get_tasks_by_priority`. Мы утвердили строгий контракт, согласно которому инструмент возвращает структурированную JSON-строку. В случае успеха структура имеет вид `{"status": "ok", "count": X, "items": [...]}`. Любые ошибки (неверный приоритет, выход лимита за границы 1..50 или сбой хранилища) перехватываются внутри инструмента через `try/except` и возвращаются агенту в формате `{"status": "error", "message": "..."}` без выброса исключения в основной поток. Если задачи по указанному критерию отсутствуют, это интерпретируется как успешное выполнение с пустым списком, а не как ошибка.

## Последствия
* **Плюсы:** ИИ-агент общается с кодом To-Do листа через безопасную границу. Модель гарантированно получает понятные текстовые подсказки об ошибках вместо ломающих её работу системных трейсбэков Windows/Python.
* **Минусы:** Требуется писать много однотипного кода валидации (проверки диапазонов `limit` и вхождения строк `priority`/`status` в допустимые списки) вручную внутри функции инструмента, так как сам ИИ-фреймворк CrewAI может передавать туда случайные данные.

## Наблюдения из трассы
Логи тестирования (файлы от `run-01.log` до `run-04.log`) показали, что локальная модель `qwen3:4b-instruct` успешно распознает назначение docstring инструмента `get_tasks_by_priority` и выполняет Function Calling. 
* В сценарии с неверным приоритетом (`priority='urgent'` в `run-02.log`), инструмент вернул структурированную ошибку. 
* Агент CrewAI успешно прочитал сообщение из поля `message`, не «уронил» процесс и смог переформулировать запрос (самокорректироваться) либо вежливо сообщил пользователю о недопустимости такого параметра.

## Когда пересмотреть
Решение по архитектуре инструмента следует пересмотреть при переходе на более крупные ИИ-фреймворки, при росте количества доступных ИИ-инструментов (более 10 штук), либо при необходимости разделения монорепозитория To-Do листа и ИИ-компонентов на отдельные микросервисы.
