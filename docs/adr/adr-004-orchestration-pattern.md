# ADR 004: Паттерн оркестрации Crew

**Статус:** Принято
**Дата:** 16.11.2026
**Команда:** команда проекта `app-conf-project-todo-list`

## Контекст

В рамках практики 4 разрабатывается мультиагентная система CrewAI, которая по запросу разработчика исследует существующий эндпоинт бэкенда и создаёт для него pytest-тест.

Задача определена в `docs/crew-design.md`, раздел 1:

«Создай pytest-тест для `GET /version`, который проверяет HTTP 200 и наличие в JSON-ответе полей `version` и `team`».

Обработчик `version` расположен в `main.py`. Его ответ содержит версию приложения и название команды. Для проверки этого поведения не требуется работающая база данных.

В предыдущих практиках использовался один агент с инструментами исследования кода и документации. Ограничение `max_iter=5` не позволяет надёжно выполнить весь цикл: найти эндпоинт, прочитать его реализацию, определить ожидаемый ответ, записать тест, проверить его линтером и исправить обнаруженные ошибки.

Поэтому работу необходимо разделить между агентами.

Система работает в общем репозитории бэкенда и ИИ-помощника. Бэкенд разрешено только читать. Сгенерированные тесты записываются в каталог `generated/` через защищённый Tool.

Для запуска используется локальный Ollama с моделью `qwen3:4b-instruct`. На CPU один вызов LLM ориентировочно занимает 1–2 минуты. Поэтому количество вызовов и ограничения агентов существенно влияют на продолжительность работы.

## Рассмотренные варианты

### 1. Один агент со всеми Tools

Один агент самостоятельно исследует код, создаёт файл и проверяет его.

**Преимущества:**
- простая архитектура;
- не требуется передавать контекст между агентами.

**Недостатки:**
- `max_iter=5` может не хватить на полный цикл;
- увеличение `max_iter` повышает риск длительных и бесполезных повторений;
- одному агенту приходится одновременно решать задачи исследования и написания кода;
- повышается риск создания теста по неполным сведениям.

Вариант не выбран.

### 2. Sequential: Исследователь → Кодер

Два агента последовательно выполняют заранее определённые задачи.

Исследователь ищет эндпоинт через `search_codebase`, читает исходный код через `read_file`, при необходимости обращается к `search_docs` и формирует структурированный итог с источниками.

Кодер получает итог Исследователя через `Task.context`, записывает тест инструментом `write_generated`, проверяет его через `run_linter` и при необходимости исправляет ошибки.

**Преимущества:**
- фиксированный и понятный порядок выполнения;
- чёткое разделение ответственности;
- каждому агенту доступны только необходимые Tools;
- не требуется дополнительный Manager-агент;
- число вызовов LLM ограничено параметром `max_iter`;
- легко анализировать трассу выполнения.

**Недостатки:**
- Кодер получает итог Исследователя, а не всю историю ответов его Tools;
- если Исследователь не передаст важные сведения, Кодер может создать некорректный тест;
- два агента требуют нескольких последовательных обращений к LLM.

Вариант выбран.

### 3. Hierarchical с Manager-агентом

Manager распределяет задания между Исследователем и Кодером и контролирует исполнение.

**Преимущества:**
- возможность управлять распределением работы;
- подходит для более сложных задач с изменяющимися требованиями.

**Недостатки:**
- дополнительные вызовы LLM для поручений и обработки результатов;
- более сложная структура;
- на текущей задаче порядок действий заранее известен, поэтому Manager не даёт существенного преимущества;
- возрастает длительность запуска на локальной модели.

Вариант не выбран.

### 4. Делегирование (`allow_delegation=True`)

Агенты могут обращаться друг к другу с вопросами и поручениями.

**Преимущества:**
- гибкость взаимодействия;
- возможность уточнения недостающих данных между агентами.

**Недостатки:**
- число дополнительных обращений к LLM заранее неизвестно;
- возможны циклы делегирования;
- сложнее обеспечить предсказуемое время выполнения;
- для двух заранее определённых задач свободное делегирование избыточно.

Вариант не выбран.

## Решение

Выбран паттерн **Sequential** (`Process.sequential`) с двумя агентами: Исследователь и Кодер.

**Исследователь** использует `search_codebase`, `read_file` и `search_docs`, чтобы найти обработчик `GET /version`, изучить его поведение и подготовить подтверждённые исходным кодом сведения.

**Кодер** использует `write_generated` и `run_linter`, чтобы создать `generated/test_version.py`, проверить файл Ruff и исправить обнаруженные ошибки.

Первый Tool практики 1 — `get_tasks_by_priority` — не включается в Crew, поскольку он не нужен для этой задачи.

**Передача контекста:** итог Исследователя передаётся Кодеру через `Task.context`. Итог должен содержать метод и путь эндпоинта, файл и функцию-обработчик, ожидаемый HTTP-статус, поля ответа, способ импорта приложения и ссылки на источники.

Если Исследователь не смог подтвердить ожидаемое поведение, Кодер не должен создавать тест на основе предположений.

**Размещение результата:** только `generated/test_version.py` в репозитории помощника. Запись за пределами разрешённого каталога запрещена. Перезапись допустимого тестового файла разрешается для исправления ошибок линтера.

**Цикл исправления:** одна попытка исправления после первой проверки Ruff. Кодер выполняет последовательность «запись → линтер → исправление → повторный линтер → итог».

**Ограничения:** `max_iter=5` у каждого агента, `max_execution_time=1800` секунд, `allow_delegation=False`, долговременная память CrewAI отключена.

**Оценка числа вызовов LLM:**

- Исследователь: 3–4 вызова;
- Кодер: 3–5 вызовов;
- Всего: ориентировочно **6–9 вызовов LLM** за один запуск.

При оценке 1–2 минуты на вызов предполагаемая продолжительность — **6–18 минут на CPU**.

Это прогноз до первого запуска, а не фактические измерения.

После выполнения практики 4 реальные показатели будут записаны в `ai/traces/run-p4-01.log` и внесены в этот ADR.

## Последствия

**Что становится проще:**

- Исследование эндпоинта и генерация теста разделены между двумя специализированными агентами.
- У каждого агента ограниченный набор инструментов.
- Порядок выполнения фиксирован и не зависит от дополнительных решений Manager-агента.
- Можно отдельно проверять качество передачи контекста и результат генерации.
- Кодер может исправлять ошибки Ruff без вмешательства в исходный код бэкенда.

**Что становится сложнее:**

- Необходимо точно определить состав итогового сообщения Исследователя.
- Требуется поддерживать безопасный инструмент записи файлов.
- `run_linter` должен работать с двумя разрешёнными корнями.
- Для воспроизводимого запуска сгенерированных тестов необходимы `pytest.ini`, `requirements-generated.txt` и `generated/conftest.py`.
- Нужно сохранять трассу выполнения и измерять фактическую стоимость работы агентов.

**Чем платим:**

- Дополнительным временем на несколько вызовов LLM.
- Необходимостью поддерживать согласованность `docs/crew-design.md` и кода Crew.
- Риском потери важных сведений при передаче итогового ответа Исследователя Кодеру.

**Как ограничиваем риски:**

- Обязательные поля итога Исследователя перечислены в архитектуре и ожидаемом результате его задачи.
- Каждый факт должен иметь источник.
- Если сведений недостаточно, тест не создаётся.
- `max_iter=5` предотвращает неограниченные попытки исправления.
- `write_generated` ограничивает запись каталогом `generated/`.
- Ruff проверяет синтаксис и статические правила, а функциональную корректность теста отдельно проверяет человек через pytest.

Результат запуска должен быть воспроизводимым: сохраняются сгенерированный тест, трасса, число вызовов LLM, время выполнения и результаты проверок.


## Результаты первого запуска CrewAI

**Дата запуска:** 16.11.2026.

**Задача:** создать pytest-тест для `GET /version`, проверяющий HTTP 200 и поля `version`, `team` без работающей базы данных.

**Трасса:** `ai/traces/run-p4-01.log`.

**Фактические показатели:**

- Вызовов LLM: **9**.
- Продолжительность: **3,0 минуты**.
- Исследователь нашёл обработчик `version` в `main.py`, изучил исходный код и использовал `search_docs`.
- Кодер создал `generated/test_version.py` инструментом `write_generated`.
- Кодер дважды проверил файл инструментом `run_linter`.
- В обеих проверках Ruff обнаружил ошибку `I001` — неправильный порядок импортов.
- Кодер не смог самостоятельно устранить замечание за одну разрешённую итерацию исправления.

**Ручное исправление:**

После завершения Crew человек выполнил:

`ruff check --isolated --no-cache --fix generated/test_version.py`

Результат: `1 fixed, 0 remaining`.

Повторная проверка без `--fix`: `All checks passed!`.

**Результаты pytest:**

- `python -m pytest generated -q` — **2 passed, 1 warning**.
- `python -m pytest -q` — **51 passed**.

Предупреждение связано с устаревающим интерфейсом Starlette/AnyIO и не повлияло на прохождение тестов.

**Проблемы трассировки:**

При запуске в PowerShell возникали ошибки кодировки `charmap` при выводе символов CrewAI. Часть русскоязычного вывода оказалась нечитаемой. Это ограничивает качество трассы и требует исправления кодировки при последующих запусках.

**Вывод:**

Sequential-оркестрация Researcher → Coder позволила найти обработчик и создать работоспособный тест. Фактическое число вызовов LLM соответствует верхней границе прогноза (9 вызовов), а продолжительность оказалась меньше ожидаемой.

Однако полный цикл автоматического исправления Ruff не завершился успешно: потребовалось вмешательство человека. Это ограничение необходимо учитывать при дальнейшем развитии Crew.

## Когда пересмотреть

Решение следует пересмотреть в следующих случаях:

1. Фактическое число вызовов LLM или продолжительность запуска значительно превысит оценку 6–9 вызовов и 6–18 минут.
2. Исследователь регулярно будет передавать Кодеру недостаточно данных для написания корректного теста.
3. Кодер не сможет завершать цикл исправления линтера в пределах `max_iter=5`.
4. Появятся более сложные задачи, требующие динамического распределения работы между несколькими агентами.
5. В цикле 5 станет доступна OpenAPI-схема бэкенда, которую можно будет использовать как дополнительный источник сведений об API.
