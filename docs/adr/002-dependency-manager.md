# ADR 002: Выбор менеджера зависимостей

## Статус

Предложено

Документ предлагает сохранить Poetry. До обсуждения и approval команды это не утверждённое решение. По заданию PR с ADR остаётся открытым до практики №3.

## Контекст

Команда 404 из четырёх человек разрабатывает To-Do List API на FastAPI. Планируются PostgreSQL, SQLAlchemy и Alembic. Для промежуточных демо каждые две недели и финального релиза нужны воспроизводимые зависимости на компьютерах разработчиков, в Docker и будущей CI.

**Текущее состояние**, проверено по `main`, коммит `aff713b792d4691b3f3bf763b8d05c6e182f9b1d`:

- `pyproject.toml` содержит две прямые зависимости: FastAPI и Uvicorn; backend сборки — `poetry-core`.
- `poetry.lock` создан Poetry 2.4.3, имеет формат 2.1, содержит 19 пакетов, связи зависимостей и SHA-256 хеши артефактов. Все пакеты относятся к группе `main`; dev-группа пока отсутствует.
- README предлагает `pip install -r requirements.txt`, хотя файлы Poetry уже закоммичены.
- `requirements.txt` смешивает библиотеки приложения с Poetry и его зависимостями. Это похоже на снимок общего окружения; происхождение файла не подтверждено. Разделения прямых, транзитивных и инструментальных зависимостей в нём нет, хешей нет.
- README указывает Python 3.11, `pyproject.toml` — `>=3.11`, а метаданные `poetry.lock` — `>=3.12`. Перед использованием lock для Python 3.11 это расхождение нужно устранить.
- `.venv/` уже находится в `.gitignore`; отдельный PR, повторно добавляющий эту строку, не нужен.
- Dockerfile и CI-конфигурации пока отсутствуют. `pytest`, `ruff`, `black`, `mypy`, SQLAlchemy и Alembic перечислены в README как стек, но не объявлены в `pyproject.toml`.

**Опыт команды:** наличие файлов показывает, что Poetry уже применялся, но не подтверждает уровень владения им каждым участником. Индивидуальный опыт с pip, Poetry и uv нужно уточнить на обсуждении. Выбор ниже опирается на состояние репозитория, без предположения о личном опыте участников.

**Проблема:**

1. Два конкурирующих способа установки могут давать разные окружения.
2. Установка из общего `requirements.txt` приносит инструменты, которые не нужны приложению.
3. Несогласованные ограничения Python мешают доверять воспроизводимости сборки.
4. Нужен единый порядок добавления библиотек и отдельная группа инструментов разработки.
5. Docker и CI должны устанавливать согласованные версии из lock, без незаметного обновления зависимостей.

Это технические проблемы, найденные в репозитории; список проблем, фактически обсуждённых на воркшопе, команда должна сверить с ними.

## Рассмотренные варианты

Сравнение по документации инструментов и файлам проекта. Скорость на этом проекте не измерялась.

| Критерий | A: pip + requirements.txt | B: Poetry | C: uv |
|---|---|---|---|
| Прямые и транзитивные зависимости, хеши | Снимок `pip freeze` хранит плоский список; в текущем файле хешей нет. Для строгой установки нужны полный список и хеши | Прямые зависимости в `pyproject.toml`, разрешённый граф и хеши артефактов в `poetry.lock`; это уже есть в проекте | Прямые зависимости в `pyproject.toml`, граф и хеши в `uv.lock`; нужно создать новый lock |
| Версия Python | Интерпретатор выбирается отдельно; текущий requirements её не задаёт | `requires-python` и `poetry env use`; диапазон поддержки должен совпадать с lock и Docker | `requires-python`, выбор интерпретатора через `.python-version` / `uv python pin` |
| Основные и dev-зависимости | Обычно отдельные requirements-файлы; в текущем файле разделения нет | Группы зависимостей, например `poetry add --group dev pytest` | Группы зависимостей, например `uv add --dev pytest` |
| Строгая установка | `pip install --require-hashes -r requirements.txt` при полном файле с хешами; удаление лишнего из окружения не выполняется | `poetry check --lock` перед `poetry sync --no-root`; для образа только группа `main` | `uv sync --locked`; устаревший lock приводит к ошибке, вместо его обновления |
| Скорость | Замеров нет; зависит от сети, кэша и пакетов | Замеров нет; для малого проекта приемлемость нужно проверить пробной установкой | Инструмент ориентирован на высокую скорость; выигрыш для команды нужно измерить |
| Docker (гипотеза) | Использовать pip из базового образа; обеспечить строгий requirements | Отдельно установить фиксированную версию Poetry, затем синхронизировать окружение по lock | Добавить бинарный uv фиксированной версии и синхронизировать окружение по `uv.lock` |
| Стоимость перехода | Очистить requirements, отделить dev-пакеты, добавить хеши и правила обновления | Минимальная: сохранить существующие файлы, согласовать Python и обновить README | Пересоздать lock, проверить совместимость и заменить команды в README и будущем Docker/CI |
| Документация и освоение | Официальная документация pip; часть правил команда должна организовать отдельно | Официальная документация по lock, группам и окружениям; файлы уже есть | Официальная документация по проектам, lock и Docker; потребуется освоить новый процесс |
| Опыт команды | Подтверждённая инструкция pip есть в README; индивидуальный опыт неизвестен | Факт использования подтверждается `poetry.lock`, индивидуальный опыт неизвестен | В репозитории следов использования нет; индивидуальный опыт неизвестен |

### Вариант A: pip + requirements.txt

**Суть:** устанавливать зависимости pip из requirements в отдельно созданное виртуальное окружение.

**Плюсы:** pip доступен в обычных Python-окружениях; простой старт для небольшого приложения.

**Минусы:** текущий файл требует очистки; разделение зависимостей, контроль Python и получение полного списка с хешами нужно организовать отдельно.

**Подходит ли нам:** с оговорками. Возможен, но сейчас означает отказ от уже существующего lock и дополнительный ручной процесс.

### Вариант B: Poetry

**Суть:** описывать зависимости проекта в `pyproject.toml`, фиксировать разрешённые версии в `poetry.lock`, устанавливать согласованное окружение Poetry.

**Плюсы:** используется в репозитории; поддерживает lock и группы; переход требует меньше изменений.

**Минусы:** отдельный инструмент установки; текущие Python-ограничения не согласованы; нужно обновить инструкции pip.

**Подходит ли нам:** да, после исправления несогласованности Python и пробной установки.

### Вариант C: uv

**Суть:** управлять проектом через `pyproject.toml`, `uv.lock` и команды uv; использовать средства выбора Python и синхронизации окружения.

**Плюсы:** единый процесс для окружения и зависимостей; `--locked` позволяет запретить автоматическое изменение lock.

**Минусы:** необходимо создать новый lock и проверить результат; практический выигрыш скорости для этого проекта не измерен.

**Подходит ли нам:** да, технически подходит. Пока не предлагаем переход, потому что преимущество для текущего маленького приложения не подтверждено, а Poetry уже используется.

## Решение

**Предлагаем сохранить Poetry**, сделать `pyproject.toml` и `poetry.lock` единственным источником зависимостей приложения. Для первого воспроизводимого процесса предлагаем Poetry **2.4.3** — версию, указанную в заголовке существующего lock. Это выбор для проекта, а не утверждение о последней версии Poetry.

### Как ставятся зависимости

**Предварительное исправление**, отдельной задачей реализации:

1. Сохранить Python 3.11 из README; установить в `pyproject.toml` `requires-python = ">=3.11,<3.12"`.
2. Выбрать локальный Python 3.11 командой `poetry env use 3.11`.
3. Выполнить `poetry lock`, затем `poetry check --lock`. Не менять метаданные или хеши lock вручную. При несовместимости пакетов подобрать совместимые ограничения средствами Poetry и проверить diff.
4. Обновить README: установка через Poetry вместо `pip install -r requirements.txt`. Удаление текущего requirements либо его замена на автоматически экспортируемый файл — отдельный согласованный шаг, не второй источник истины.

**Для разработчика**, после согласования lock, из корня репозитория:

```bash
poetry --version
poetry config virtualenvs.in-project true --local
poetry env use 3.11
poetry check --lock
poetry sync --no-root
poetry run uvicorn main:app --reload
```

`--no-root` нужен, поскольку текущее приложение — `main.py`, без настроенного устанавливаемого Python-пакета. Локальный `poetry.toml`, созданный `--local`, не включаем в PR с этим ADR; правила его игнорирования при необходимости добавляем отдельной настройкой.

**Для будущего Dockerfile — гипотеза**, которую проверим на практике №3:

```dockerfile
FROM python:3.11-slim
WORKDIR /app
ENV POETRY_HOME=/opt/poetry \
    POETRY_VIRTUALENVS_IN_PROJECT=true \
    PATH="/opt/poetry/bin:/app/.venv/bin:$PATH"
RUN python -m venv /opt/poetry \
    && /opt/poetry/bin/pip install --no-cache-dir poetry==2.4.3
COPY pyproject.toml poetry.lock README.md ./
RUN poetry check --lock \
    && poetry sync --only main --no-root --no-interaction
COPY main.py ./
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

Poetry и его зависимости устанавливаются в отдельное окружение `/opt/poetry`, библиотеки приложения — в `/app/.venv`. Это сохраняет инструмент при синхронизации окружения приложения. Перед добавлением миграций в образ нужно дополнительно скопировать их файлы. Этот фрагмент не добавляет подключение к БД. Сборка здесь не запускалась: Docker недоступен в текущем окружении.

### Правила управления зависимостями

1. Коммитим `pyproject.toml` и `poetry.lock` вместе, когда меняются зависимости. `.venv/`, локальные настройки и секреты не коммитим.
2. Добавляем библиотеку командой `poetry add <пакет>`; удаляем через `poetry remove <пакет>`. Например, SQLAlchemy, Alembic и `psycopg[binary]` добавляются отдельной задачей при реализации БД.
3. Инструменты разработки добавляем в группу `dev`: `poetry add --group dev pytest ruff black mypy`. Это план: сейчас группа и эти зависимости отсутствуют.
4. После появления группы `dev` разработчик устанавливает её явно: `poetry sync --with dev --no-root`; Docker устанавливает только `main`.
5. Для проверки согласованности выполняем `poetry check --lock`; обычная установка не должна обновлять lock. Изменения версий проводим отдельным PR, проверяя diff и запуск приложения.
6. Poetry не добавляем в зависимости самого приложения. Версию инструмента фиксируем в инструкции и будущем Dockerfile/CI.
7. PR с ADR содержит документацию; исправление диапазона Python, lock, README и зависимостей выполняется отдельным PR по правилам CONTRIBUTING.

## Обоснование решения

1. **Стоимость перехода:** манифест и lock уже есть. Проще исправить существующий процесс, чем одновременно менять менеджер и начинать контейнеризацию.
2. **Воспроизводимость:** lock содержит конкретные версии и хеши; согласование Python и проверка lock становятся явными шагами установки.
3. **Разделение окружений:** группа `dev` позволяет отделить будущие тесты и линтеры от библиотек, нужных API.
4. **Размер команды и релизы:** четыре участника и демо раз в две недели выигрывают от одного понятного процесса обновления зависимостей.
5. **Неизвестный опыт и скорость:** не приписываем участникам навыки и не используем непроверенные результаты замеров. Если пробная установка покажет существенные проблемы, решение можно пересмотреть в пользу uv до принятия ADR.

## Последствия

### Положительные (+)

- Один источник зависимостей для разработчиков, Docker и будущей CI.
- Используем существующий формат проекта; миграция на другой lock не требуется.
- Проверка lock и отдельная dev-группа делают процесс установки понятнее.

### Отрицательные (-)

- Каждый участник должен установить Poetry выбранной версии и доступный Python 3.11.
- Нужно исправить Python-ограничения, пересоздать lock и обновить README.
- Docker-сборка получает дополнительный инструмент; оптимизацию размера образа откладываем до соответствующей практики.

### Риски и митигация

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Lock не соответствует манифесту или Python образа | Высокая: расхождение диапазонов уже найдено | Высокое | Согласовать `requires-python`, пересоздать lock через Poetry, выполнить `check --lock` и пробную установку на Python 3.11 |
| Разработчики продолжают устанавливать общий requirements | Средняя | Среднее | Заменить команды в README; объяснить единый источник зависимостей, согласовать судьбу requirements |
| Poetry пытается установить отсутствующий пакет проекта | Средняя | Среднее | Использовать `--no-root` для текущей структуры `main.py` |
| Lock конфликтует при параллельном добавлении библиотек | Средняя | Среднее | После слияния манифеста пересоздать lock Poetry, не редактировать хеши вручную |
| Гипотеза Dockerfile не проходит реальную сборку | Средняя | Высокое | На практике №3 выполнить сборку, проверить версии и `/health`; затем скорректировать Dockerfile и ADR |
