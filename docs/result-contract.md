# Контракт результата помощника

**Команда:** 404  
**Бэкенд:** `app-conf-project-todo-list`, стенд Docker Compose  
**Коммит бэкенда:** `250fa06`

## 1. Схема и код

Эндпоинт — `GET /version`.

По OpenAPI ожидается успешный ответ со статусом `200`. Схема указывает тип содержимого `application/json`, но структура объекта ответа в ней не описана.

| Что | В схеме | В коде | Откуда берём для теста |
|---|---|---|---|
| Метод и путь | `GET /version` | `main.py:62`, декоратор `@app.get("/version")` | OpenAPI и декоратор обработчика |
| Параметры и тело запроса | Параметров и тела нет | `main.py:63`, функция `version()` без аргументов | Запрашиваем `/version` без параметров и тела |
| Успешный статус | `200` | `main.py:62–65`, обработчик возвращает словарь без переопределения статуса | OpenAPI и реализация обработчика |
| Тело ответа | `application/json`, схема тела `{}` | `main.py:65` возвращает `app.version` и `TEAM_NAME`; версия задана на строке 14, команда — на строке 20 | Из кода берём `version="0.2.0"` и `team="404"` |
| Ошибки | Для операции заявлен ответ `200` | Обработчик не объявляет отдельные ошибки и не обращается к БД | В эту практику входит тест успешного ответа |

Статус `200` совпал с предсказанием по схеме. Имена и значения полей удалось определить по коду. Ответ стенда на `GET /version`: `{"version":"0.2.0","team":"404"}`.

## 2. Контракт результата

Контракт описывает итог последней задачи Crew. Кодер записывает Python-файл через `write_generated`. В итоговый объект входит путь к файлу, сведения о тест-кейсах, вывод линтера в пересказе Кодера и записка для человека.

Все поля обязательного минимума должны присутствовать. Если значение по смыслу отсутствует, используется пустая строка или пустой список там, где это разрешено контрактом.

### Итог Crew

| Поле | Тип | Ограничение | Что при нарушении |
|---|---|---|---|
| `search_status` | Одно из трёх значений | `found`, `not_found` или `tool_error` | Отказ формата при недопустимом значении. Отказ кода, если при статусе `not_found` или `tool_error` в текущем запуске записан файл теста. Человек сверяет статус с трассой. |
| `test_file` | Строка | Путь вида `generated/test_<имя>.py`; пустая строка, если теста нет | Отказ формата при неверном шаблоне пути. Отказ кода при пустом пути со статусом `found`, отсутствующем файле или файле, который не обновлён в текущем запуске. |
| `test_cases` | Список объектов | Не более трёх элементов. При `found` нужен хотя бы один кейс. При `not_found` и `tool_error` ожидается пустой список. | Отказ формата при неверном типе или превышении лимита. Отказ кода при пустом списке со статусом `found`. Человек отмечает непустой список при `not_found` или `tool_error`. |
| `linter_result` | Строка | Итог последнего вызова `run_linter` | Отказ формата при неверном типе или отсутствии поля. Человек сверяет значение с фактическим выводом Ruff. |
| `note` | Непустая строка | Объясняет, что проверяет тест или почему он не записан. При ошибке инструмента содержит его сообщение. Итог pytest в записку не входит. | Отказ формата при пустой строке или отсутствии поля. Человек сверяет содержание с трассой. |

### Элемент `test_cases`

| Поле | Тип | Ограничение | Что при нарушении |
|---|---|---|---|
| `name` | Строка | Имя функции начинается с `test_` и соответствует шаблону каркаса | Отказ формата при неверном имени. Человек сверяет имя с функцией в записанном файле. |
| `method` | Одно из пяти значений | `GET`, `POST`, `PUT`, `PATCH` или `DELETE` | Отказ формата при недопустимом методе. Отказ кода, если пара `method` и `path` отсутствует в полной OpenAPI-схеме. |
| `path` | Строка | Начинается с `/` и совпадает с путём в схеме | Отказ формата при неверном шаблоне. Отказ кода при несовпадении пары метода и пути со схемой. |
| `expected_status` | Целое число | От 100 до 599. Для `GET /version` ожидается `200`. | Отказ формата при нарушении типа или диапазона. Человек сверяет значение с обработчиком и проверкой в тесте. |
| `expected_fields` | Список объектов `{field, value}` | Для `GET /version` ожидаются `version="0.2.0"` и `team="404"` | Отказ формата при неверной структуре. Человек сверяет имена и значения с кодом и проверками в тесте. |
| `source` | Непустая строка | Указывает файл и строки, где подтверждаются ожидаемые статус и тело ответа | Отказ формата при пустой строке или отсутствии поля. Человек проверяет источник. |

Результат `pytest` хранится отдельно. Команду запускает разработчик, а фактический вывод прикладывается к Pull Request.

### Свои поля

Дополнительных полей в этой итерации нет. Передача Исследователь → Кодер остаётся текстовой. Структурируется итог последней задачи Crew.

### Примеры проверки контракта

- `path="/versions"` при `method="GET"` проходит проверку формы. Код отклоняет результат, поскольку такой пары нет в схеме.
- `search_status="found"` при `test_file=""` проходит проверку формы. Код отклоняет результат, поскольку для найденного эндпоинта должен быть записан тест. Уже существующий файл автоматически не удаляется.

## 3. Правила доступа

| № | Что | Правило курса | Как выполняется у нас |
|---|---|---|---|
| 1 | Код и документация бэкенда | Только чтение через Tools | Исследователь использует `search_codebase`, `read_file` и `search_docs`. |
| 2 | `GET /openapi.json` | Адрес из настроек; у Tool нет аргументов URL и метода | `get_openapi_schema` получает адрес из `AI_BACKEND_URL`. Для локального стенда используется `http://127.0.0.1:8000`. |
| 3 | Другие эндпоинты и методы | Агент их не вызывает | Tool чтения схемы не принимает произвольный URL или HTTP-метод. `GET /version` проверяет человек или локальный тест через `TestClient`. |
| 4 | Стенд | Поднимает человек | Разработчик запускает `docker compose up -d --build`. Если схема недоступна при предварительной проверке, Crew не запускается. |
| 5 | pytest | Запускает человек; из кода `ai/` не вызывается | После проверки сгенерированного файла разработчик запускает `python -m pytest generated -q` и прикладывает фактический вывод к PR. |
| 6 | Запись | Только `write_generated` и только в `generated/` | Для этой задачи целевой файл — `generated/test_version.py`. |
| 7 | Изменения бэкенда | Только Pull Request, который делают и принимают люди, неделя 12 | В практике 5 изменения касаются помощника и тестов. |
| 8 | Схема как контент | Данные, а не инструкции; при облачном пути уходит провайдеру | Используем локальную Ollama. Текстовые описания из OpenAPI исключаются из сводки для агента. |

## 4. Сбои запроса схемы

| № | Сбой | Повторять? | Таймаут × попытки | Что получит агент или разработчик |
|---|---|---|---|---|
| С1 | Стенд не поднят или соединение разорвано | Да, один повтор | Подключение до 5 с, всего две попытки | Сообщение, что стенд не отвечает и схему получить не удалось. |
| С2 | Истёк таймаут чтения | Да, один повтор | Чтение до 10 с, всего две попытки | Сообщение, что стенд не ответил за 10 секунд. |
| С3 | `/openapi.json` вернул `404` | Нет | Одна попытка | Сообщение о том, что схема отключена и на стенде нужен `APP_ENV=dev`. |
| С4 | Стенд вернул `5xx` | Да, один повтор | Подключение до 5 с, чтение до 10 с, всего две попытки | Сообщение с фактическим HTTP-статусом. |
| С5 | Ответ `200`, но тело не JSON, отсутствует объект `paths` или сводка слишком большая | Нет | Одна попытка | При неверном ответе — сообщение о формате или схеме. Для валидной большой схемы — сокращённая сводка с `truncated: true`. |
| С6 | В `description` схемы находится инструкция | Нет | Дополнительный запрос не нужен | Текст описания исключается из сводки, которую получает агент. |

С7, асинхронная задача — для `GET /version` отсутствует. Обработчик возвращает ответ в рамках исходного HTTP-запроса.
