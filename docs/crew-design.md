# Архитектура Crew помощника

**Команда:** команда проекта `app-conf-project-todo-list`
**Бэкенд:** собственный бэкенд To-Do List, общий репозиторий бэкенда и ИИ-помощника, `AI_REPO_ROOT=.`
**Путь LLM:** А — локальный Ollama, модель `qwen3:4b-instruct`; эмбеддинги — `qwen3-embedding:0.6b`
**Дата:** 16.11.2026

## 1. Задача разработчика (входной билет)

**Как разработчик сказал бы её в чате:**

«Создай pytest-тест для эндпоинта `GET /version`. Проверь, что запрос возвращает HTTP 200 и JSON с полями `version` и `team`. Тест должен выполняться без работающей базы данных».

**Эндпоинт:** `GET /version`.

**Обработчик:** `main.py`, функция `version`, строки 62–65 в ранее проверенной версии файла.

**Что проверяет тест (одно поведение):**

Запрос `GET /version` → HTTP 200, тело ответа содержит поля `version` и `team`. Их значения формируются приложением: версия берётся из `app.version`, название команды — из `TEAM_NAME`.

**Откуда известно, что так и должно быть:**

Файл `main.py`:

- строка 62 — декоратор `@app.get("/version")`;
- строка 63 — функция `version`;
- строка 65 — возврат словаря `{"version": app.version, "team": TEAM_NAME}`.

Эндпоинт не обращается к PostgreSQL и не требует работающей базы данных. При этом для импорта приложения может потребоваться заданная переменная окружения `DATABASE_URL`.

**Файл результата:** `generated/test_version.py` в репозитории помощника.

## 2. Агенты

| Агент | `role` | `goal` одной фразой | `backstory`: главное правило поведения | Итог задачи: что отдаёт |
|---|---|---|---|---|
| Исследователь | Researcher | Найти обработчик эндпоинта и подтвердить его поведение исходным кодом и документацией. | Использовать только факты из `read_file`, `search_codebase` и `search_docs`; читать необходимые строки исходного файла; указывать источники; не придумывать отсутствующие данные. | Структурированное описание эндпоинта, обработчика, ожидаемого HTTP-статуса, полей ответа, способа импорта приложения и источников. |
| Кодер | Coder | Создать pytest-тест по результату Исследователя, проверить его линтером и исправить обнаруженные ошибки. | Работать только с подтверждёнными фактами Исследователя; записывать тест через `write_generated` исключительно в `generated/`; после записи вызывать `run_linter`; при ошибке исправлять файл и повторять проверку. | Путь к созданному тесту, описание проверяемого поведения, результат линтера и сведения о выполненных исправлениях. |

**Почему не один агент с пятью Tools:**

Один агент с `max_iter=5` может не успеть найти эндпоинт, изучить обработчик, написать файл, проверить его линтером и исправить ошибки.

Разделение работы позволяет Исследователю сосредоточиться на сборе подтверждённых фактов, а Кодеру — на генерации и проверке кода. Каждый агент получает только необходимые инструменты.

При этом критически важно передать Кодеру все найденные сведения: CrewAI передаёт следующей задаче итог предыдущей задачи, а не полную историю вызовов её Tools.

## 3. Tools по агентам

| Tool | У какого агента | Зачем ему — или «не нужен», потому что |
|---|---|---|
| `get_tasks_by_priority` — Tool практики 1 | Не используется | Инструмент предназначен для бизнес-логики To-Do и не требуется для исследования эндпоинта или генерации pytest-теста. Он уже исключён из активного набора инструментов помощника в предыдущих практиках. |
| `read_file` | Исследователь | Прочитать `main.py`, проверить обработчик `version` и подтвердить ожидаемый ответ. |
| `search_codebase` | Исследователь | Найти объявление `GET /version` и функцию `version` в исходном коде. |
| `run_linter` | Кодер | Проверить созданный тест Ruff, получить замечания и повторно проверить файл после исправления. |
| `search_docs` | Исследователь | Найти сведения об эндпоинте в документации проекта и подтвердить источники; не подменять факты из кода предположениями. |
| `write_generated` — новый Tool практики 4 | Кодер | Безопасно создавать и перезаписывать разрешённые тестовые файлы исключительно в `generated/`. |

**Подготовка индекса:**

Индекс для `search_docs` строится до запуска Crew командой:

```powershell
python -m ai.tools.rag_pipeline build
```

В нашем монорепозитории используются:

- `AI_REPO_ROOT=.`;
- `AI_INDEX_DIR=../.chroma`;
- локальная модель эмбеддингов `qwen3-embedding:0.6b`.

Векторный индекс располагается за пределами корня проекта и не коммитится в Git.

**Новый Tool: `write_generated`.**

Без этого инструмента Кодер может только вернуть текст теста в ответе. Для практики 4 требуется именно файл, созданный агентом.

Инструмент должен:

- разрешать запись только в `generated/test_*.py`;
- запрещать выход за пределы разрешённого каталога;
- запрещать пустое содержимое;
- запрещать вложенные каталоги и неподходящие имена файлов;
- разрешать перезапись допустимого тестового файла для исправления замечаний линтера;
- не изменять исходный код бэкенда и конфигурационные файлы.

Реализация выполняется на основе обязательного каркаса `templates/generated_files.py` и проверяется тестами курса из шага 2.1 `practice-4.md`.

## 4. Паттерн оркестрации

**Паттерн:** Sequential (`Process.sequential`).

**Почему:**

Работа имеет фиксированный порядок:

1. Исследователь находит и проверяет сведения об эндпоинте.
2. Кодер получает итог Исследователя и создаёт тест.
3. Кодер проверяет тест линтером и при необходимости исправляет его.

Для этих действий не нужен отдельный агент-менеджер, который динамически назначает исполнителей.

**Manager-агент:** отсутствует.

**Делегирование (`allow_delegation=True`):** отключено у обоих агентов (`allow_delegation=False`). Задачи распределяются заранее, а свободное делегирование может привести к лишним вызовам LLM и циклам передачи поручений.

**Оценка числа вызовов LLM за запуск:**

Исследователь:

- поиск эндпоинта;
- чтение исходного кода;
- при необходимости поиск по документации;
- итоговый ответ.

Ориентировочно 3–4 вызова.

Кодер:

- запись файла;
- проверка линтером;
- при необходимости исправление;
- повторная проверка;
- итоговый ответ.

Ориентировочно 3–5 вызовов.

**Суммарная оценка: 6–9 вызовов LLM за запуск.**

Реальное число вызовов и продолжительность будут определены после запуска Crew и зафиксированы в трассе и ADR 004.

## 5. Задачи и передача контекста

| # | Задача кратко | Агент | `context`: итоги каких задач получает | `expected_output`: что именно в итоге |
|---|---|---|---|---|
| 1 | Найти и исследовать `GET /version` | Исследователь | Нет предыдущих задач | Структурированные факты: метод и путь, обработчик, исходный файл и строки, ожидаемый статус, поля JSON, способ импорта приложения, источники и статус поиска. |
| 2 | Создать и проверить pytest-тест | Кодер | Итог задачи 1 (`context=[research_task]`) | Путь `generated/test_version.py`, краткое описание теста, результат Ruff, информация об исправлениях или причина невозможности создания файла. |

**Что Исследователь передаёт Кодеру — поля итога:**

| Поле | Значение |
|---|---|
| Эндпоинт | `GET /version` |
| Исходный файл | `main.py` |
| Обработчик | `version` |
| Расположение | Строки 62–65 ранее проверенного файла |
| Ожидаемый HTTP-статус | `200` |
| Поля ответа | `version`, `team` |
| Значения полей | Формируются сервером: `app.version` и `TEAM_NAME` |
| Получение приложения | `from main import app`, затем `TestClient(app)` |
| Требуется ли работающая БД | Нет |
| Источник | `main.py`, декоратор, функция и возвращаемый словарь |
| Файл теста | `generated/test_version.py` |

Кодер не должен придумывать конкретные значения `version` и `team`: они зависят от конфигурации приложения. Тест проверяет HTTP-статус и наличие предусмотренных полей ответа.

**Если подходящего эндпоинта или подтверждения поведения не найдено:**

Исследователь явно сообщает статус `not_found`, указывает выполненные поисковые действия и недостающие данные.

Кодер не создаёт тест на основе предположений. В итоговом ответе объясняет, каких подтверждённых сведений не хватило.

**Если Tool вернул ошибку:**

Например:

- индекс документации не построен;
- модель эмбеддингов недоступна;
- файл исходного кода не удалось прочитать.

Исследователь передаёт статус ошибки, название инструмента и причину.

Если ошибка не позволяет подтвердить ожидаемое поведение, Кодер не создаёт файл и сообщает причину. Если поиск по документации недоступен, но исходный код удалось прочитать и он однозначно подтверждает поведение, Исследователь фиксирует ограничение и передаёт подтверждённые кодом факты.

**Чем подтверждены правила передачи контекста:**

Раздел `materials-4.md` «Отрывки трасс для этапа 2: Границы Исследователя»:

- случай Б — найден нерелевантный фрагмент документации;
- случай В — ошибка инструмента поиска;
- случай Г — нужная информация отсутствует в первых результатах поиска.

Также учитывается правило CrewAI: в Sequential следующая задача получает финальный итог предыдущей, а не отдельные ответы её Tools.

## 6. Цикл «генерация → линтер → исправление»

**Где лежит тест:** `generated/test_version.py` в репозитории помощника.

**Кто записывает файл:** Кодер через Tool `write_generated`.

Бэкенд напрямую не изменяется. В нашем монорепозитории это означает запрет на изменение `main.py`, `config.py`, `settings.py` и других исходных файлов приложения агентом.

**Границы записи:**

`write_generated` принимает только разрешённый путь внутри `generated/`, проверяет его на выход из каталога и запрещает неподходящие имена или пустое содержимое.

Перезапись существующего допустимого теста разрешена, поскольку она необходима для исправления ошибок линтера.

**Кто вызывает `run_linter`:** Кодер после записи тестового файла.

`run_linter` должен поддерживать два безопасных корня:

1. `AI_REPO_ROOT` — для чтения и проверки кода бэкенда.
2. `generated/` — для проверки созданного теста.

При проверке сгенерированного теста используются изолированные настройки Ruff (`--isolated`) и отключение кеша (`--no-cache`), чтобы результат не зависел от конфигурации бэкенда.

**Последовательность:**

1. Кодер создаёт `generated/test_version.py` через `write_generated`.
2. Кодер вызывает `run_linter`.
3. Если Ruff сообщает об ошибках, Кодер исправляет файл через `write_generated`.
4. Кодер повторно вызывает `run_linter`.
5. Кодер выдаёт итоговый результат.

**Максимум итераций исправления:** одна.

**Вызовы LLM у Кодера на цикл:**

(запись + линтер) × (1 + 1 исправление) + итог = 5 вызовов.

Это соответствует `max_iter=5`.

**Что после последней неудачной итерации:**

Агент прекращает попытки исправления, не скрывает ошибки и сообщает человеку путь к файлу, результат Ruff и оставшиеся замечания.

**Что линтер не проверит и кто это проверит:**

Ruff проверяет качество кода и определённые статические ошибки, но не подтверждает правильность HTTP-ответа приложения.

Человек запускает pytest из окружения помощника:

```powershell
python -m pytest generated -q
```

При необходимости человек анализирует ошибки и принимает решение о дальнейшей работе с тестом. Сам агент не запускает pytest и не изменяет бэкенд.

**`generated/` в Git:** коммитим сгенерированный тест, даже если его выполнение выявило ошибку. Это необходимо для воспроизводимого peer review: проверяющий должен видеть созданный Кодером файл и фактический результат проверки.

## 7. Память

**Контекст запуска:**

Во время одного запуска CrewAI передаёт результаты между задачами через `Task.context`. После завершения запуска этот оперативный контекст не используется как долговременная память агентов.

**Векторное хранилище:**

Документация проекта индексируется инструментом `search_docs`, как описано в `docs/rag-design.md`.

В нашем проекте:

- векторная база — ChromaDB;
- модель эмбеддингов — `qwen3-embedding:0.6b`;
- индекс располагается по пути `../.chroma`;
- исходные документы берутся из разрешённых файлов проекта;
- векторный индекс не коммитится в Git и может быть построен повторно.

**Memory CrewAI:** не включаем (`memory=False`).

Причины:

1. Для фиксированной последовательности Исследователь → Кодер достаточно контекста текущих задач.
2. Долговременная память может сохранять устаревшие факты об эндпоинтах.
3. Дополнительная обработка памяти увеличивает вычислительные затраты.
4. Нам важны воспроизводимость результатов и работа с актуальными исходными файлами.

## 8. Ограничения и результат для людей

**Ограничения агентов:**

- Исследователь: `max_iter=5`.
- Кодер: `max_iter=5`.
- Ограничение времени задачи: `max_execution_time=1800` секунд для каждого агента.
- Делегирование отключено.
- Агентам предоставляются только инструменты, необходимые для их ролей.

`max_execution_time` — дополнительное ограничение, а `max_iter` защищает от слишком длинных циклов вызовов LLM. Если выполнение превышает лимиты, код запуска должен сообщить об этом человеку без заявления об успешном создании теста.

**Оценка времени одного запуска:**

При предполагаемых 6–9 вызовах LLM и ориентировочной стоимости 1–2 минуты на вызов на CPU:

- нижняя оценка — 6 минут;
- верхняя оценка — 18 минут.

Это предварительная оценка, а не результат измерения.

После боевого запуска фактические число вызовов и продолжительность фиксируются в `ai/traces/run-p4-01.log` и ADR 004.

**Модель:**

Одна модель `qwen3:4b-instruct` через локальный Ollama используется для обоих агентов. Каждый агент получает собственный объект LLM в соответствии с каркасом практики 4.

Для поиска документации используется отдельная модель эмбеддингов `qwen3-embedding:0.6b`.

Такой подход сохраняет полностью локальный контур и не требует облачного API-ключа.

**Бэкенд не меняется:**

ИИ-помощник читает код и документацию, но не меняет исходные файлы приложения, настройки базы данных или существующие эндпоинты.

В монорепозитории запись разрешена только в специальный каталог `generated/` через защищённый инструмент.

**Что получает человек после запуска:**

1. Сгенерированный тест `generated/test_version.py`.
2. Краткое описание проверяемого поведения.
3. Ссылки на исходные файлы и строки, подтверждающие ожидаемый результат.
4. Результат проверки Ruff.
5. Трассу `ai/traces/run-p4-01.log` с выполненными действиями, длительностью и числом вызовов LLM.
6. Сообщение об ошибке, если тест не удалось создать или проверить.

**Как человек проверяет тест на неделе 8:**

Сгенерированный тест запускается через pytest из виртуального окружения помощника.

Для этого необходимы:

- `pytest` и `httpx`;
- `fastapi` и зависимости приложения;
- корректный путь импорта `main.py`;
- переменные окружения, необходимые для импорта приложения.

Файл `generated/conftest.py`, создаваемый по каркасу `templates/generated-conftest.py`, настраивает импорт приложения и тестовые значения необходимых переменных окружения, включая `DATABASE_URL`.

При этом сам тест `GET /version` не подключается к PostgreSQL, поэтому работающая база данных ему не требуется.

Обычный набор тестов проекта и сгенерированные тесты разделяются настройкой `pytest.ini` с `testpaths = tests`.

**Как тест попадает в бэкенд:**

На практике 4 сгенерированный тест остаётся в `generated/` и проходит проверку человеком.

Его возможное включение в основной набор тестов бэкенда — отдельное решение и последующая работа. Агент автоматически не переносит тест в исходные каталоги приложения и не создаёт PR от своего имени.

## Открытые вопросы к ADR 004

- Уточнить окончательное имя файла ADR: по методичке `docs/adr/004-orchestration-pattern.md`, но в нашем общем репозитории ранее использовалось соглашение `docs/adr/adr-004-orchestration-pattern.md`. Согласовать с правилами команды, прежде чем создавать файл.
- После первого запуска сравнить оценку 6–9 вызовов LLM с фактическими метриками из трассы.
- Проверить, смог ли Кодер выполнить полный цикл записи, линтера и исправления в пределах `max_iter=5`.
- Зафиксировать, какие поля Исследователя действительно дошли до Кодера и какие сведения могли потеряться при передаче.
- После выполнения практики 4 обновить ADR 004 фактическими результатами и изменить статус с «Предложено» на «Принято».
