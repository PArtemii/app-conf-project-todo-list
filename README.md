## API

Базовый URL: `http://localhost:8000`

| Метод | Путь       | Описание                                | Ответ |
|-------|------------|-----------------------------------------|-------|
| GET   | `/`        | Приветственное сообщение                | `{"message": "Hello World"}` |
| GET   | `/health`  | Проверка работоспособности сервиса      | `{"status": "healthy"}` |
| GET   | `/version` | Версия приложения и команда-владелец    | `{"version": "0.2.0", "team": "404"}` |

Интерактивная документация: `http://localhost:8000/docs` (Swagger UI) и `http://localhost:8000/redoc`.

### Примеры запросов

```bash
# macOS / Linux
curl http://localhost:8000/version

# Windows PowerShell
curl.exe http://localhost:8000/version
```

Ответ:

```json
{"version":"0.2.0","team":"404"}
```

Версия берётся из параметра `version` конструктора `FastAPI` в `main.py` и отображается в OpenAPI-схеме на `/docs`. Отдельной константы версии в проекте нет — это сделано намеренно, чтобы значение не разъезжалось.

## Практика №4: конфигурация, безопасность и Docker

### Настройки окружения

Приложение использует `pydantic-settings` (`config.py`). Для локальной настройки скопируйте `.env.example` в `.env` и заполните параметры PostgreSQL. **Не добавляйте `.env` в Git.**

| Переменная | Назначение | Значение по умолчанию |
|---|---|---|
| `APP_ENV` | Режим `dev` или `prod` | `dev` |
| `DB_CONNECT_TIMEOUT` | Тайм-аут соединения с БД, 1–60 секунд | `3` |
| `DATABASE_URL` | URL подключения к PostgreSQL | Не задан |
| `POSTGRES_USER` | Пользователь PostgreSQL в Compose | Задаётся в `.env` |
| `POSTGRES_PASSWORD` | Пароль PostgreSQL в Compose | Задаётся в `.env` |
| `POSTGRES_DB` | Имя базы данных в Compose | Задаётся в `.env` |

Docker Compose формирует `DATABASE_URL` из `POSTGRES_*` и передаёт его приложению. Для запуска вне Docker можно задать `DATABASE_URL` самостоятельно.

В режиме `dev` доступны `/docs`, `/redoc`, `/openapi.json`; в режиме `prod` эти адреса отключены.

### Запуск в Docker

```bash
docker compose up -d --build
docker compose ps
```

Проверка работоспособности: `http://localhost:8000/health`. Для остановки используйте `docker compose down` (без `-v`, если данные PostgreSQL нужно сохранить).

### Проверки перед коммитом

```bash
python -m pip install pre-commit
pre-commit install
pre-commit run --all-files
```

Хуки проверяют пробелы, окончания файлов, YAML, TOML, размер добавляемых файлов, приватные ключи и потенциальные секреты (`detect-secrets`). Базовый файл проверки — `.secrets.baseline`. После автоматических исправлений проверьте `git status` и повторите запуск хуков.

### Оптимизация Docker

Dockerfile использует две стадии сборки, непривилегированного пользователя `appuser` (UID 10001) и `HEALTHCHECK`. Установка зависимостей кешируется отдельным слоем.

| Образ | Disk usage |
|---|---:|
| Исходный одноэтапный | 285 MB |
| Первый двухэтапный | 305 MB |
| Оптимизированный двухэтапный | 268 MB |

Итоговое уменьшение относительно исходного образа — **17 MB (около 6%)**.

Подробности решения — в [ADR 003](docs/adr/003-config-security-docker.md).


## ИИ-Инструменты анализа кодовой базы (Практика 2 ИИ)

В рамках Практики 2 в систему добавлены три детерминированных инструмента для работы с исходным кодом бэкенда:
1. `search_codebase` — поиск ключевых слов (kind="text") или определений функций/классов (kind="symbol") через абстрактное синтаксическое дерево (AST) без выполнения кода.
2. `read_file` — безопасное чтение фрагментов текстовых файлов с номерами строк и автоматическим отсечением бинарных данных.
3. `run_linter` — запуск статического анализатора `ruff check` в изолированном режиме с детерминированным перехватом системных кодов возврата (0, 1, 2).

### Конфигурация безопасности (.env)
Доступ ИИ-агента жестко ограничен следующими переменными окружения:
* `AI_REPO_ROOT` — абсолютный или относительный путь к анализируемому бэкенду.
* `AI_DENY_GLOBS` — список запрещенных файлов через запятую (например, `.env*,*.pem,secrets`), по умолчанию закрывающий доступ к чувствительным данным.
* `AI_EXCLUDE_DIRS` — каталоги, которые инструмент поиска гарантированно пропускает при обходе (например, `venv,node_modules`).
* `AI_TOOL_TIMEOUT_S` — жесткий потолок времени выполнения процессов (30 секунд).

### Запуск автоматических тестов
Проект покрыт детерминированными тестами безопасности OWASP Top 10 (Excessive Agency). Для запуска тестов выполните в корневом каталоге:
```bash
python -m pytest -q
```

## Поиск по документации (Практика 3 ИИ)

В систему интегрирован RAG-пайплайн на базе векторного хранилища **ChromaDB** и локальных эмбеддингов **Ollama** (`qwen3-embedding:0.6b`).

### Что индексируется
* Документация проекта (`README.md`, `CONTRIBUTING.md`, `docs/environment-schema.md`, файлы архитектурных решений в `docs/adr/`, спецификации инструментов) и `docstrings` из исходного кода Python.
* Файлы секретов (`.env*`, `*.pem`), системные директории (`.venv`, `.git`, `.chroma`, `tests`) и сам файл проектирования `docs/rag-design.md` исключены из индекса.

### Построение и обновление индекса
Векторный индекс является производным объектом, не хранится в Git и собирается локально на машине разработчика. Перестраивать индекс необходимо вручную после каждого обновления документации в ветке `main` (`git pull`):

```bash
python -m ai.tools.rag_pipeline build
```

Для работы поиска требуется запущенный локальный сервер **Ollama** с загруженной моделью `qwen3-embedding:0.6b`.

### Новые настройки окружения (`.env`)
* `AI_INDEX_DIR` — путь к каталогу индекса ChromaDB (по умолчанию `../.chroma` для изоляции от корня монорепозитория).
* `AI_INDEX_BACKEND_GLOBS` / `AI_INDEX_ASSISTANT_GLOBS` — маски разрешенных для индексации файлов.
* `AI_EMBED_MODEL` — модель эмбеддингов в Ollama (`qwen3-embedding:0.6b`).
* `AI_EMBED_TIMEOUT_S` — таймаут запроса к Ollama при генерации векторов (300 сек).
* `AI_SEARCH_TOP_K` — количество возвращаемых фрагментов по умолчанию (3, потолок — 5).
* `AI_SEARCH_MAX_DISTANCE` — порог косинусного расстояния (2.0 — без жесткого отсечения).


## CrewAI — мультиагентная генерация тестов (Практика 4 ИИ)

В проекте реализована последовательная оркестрация двух агентов CrewAI по схеме **Researcher → Coder** (`Process.sequential`).

- **Researcher (Исследователь)** находит нужный обработчик API, изучает исходный код и документацию через `search_codebase`, `read_file` и `search_docs`.
- **Coder (Кодер)** получает результат исследования, создаёт pytest-тест через `write_generated` и проверяет его инструментом `run_linter`.

Контекст между задачами передаётся через `Task.context`. У каждого агента `max_iter=5`, время выполнения ограничено, делегирование отключено.

### Подготовка окружения

Запуск выполняется из корня репозитория в активированном виртуальном окружении Python.

Необходим локальный сервер **Ollama** и загруженные модели:

- `qwen3:4b-instruct` — LLM для агентов;
- `qwen3-embedding:0.6b` — модель эмбеддингов для поиска по документации.

Проверить установленные модели:

```powershell
ollama list
```

Перед запуском Crew необходимо построить индекс документации:

```powershell
python -m ai.tools.rag_pipeline build
```

В локальном `.env` должны быть настроены параметры подключения к Ollama, корень анализируемого репозитория (`AI_REPO_ROOT`) и каталог индекса (`AI_INDEX_DIR`). Секреты и локальный каталог `.chroma/` не добавляются в Git.

### Запуск Crew

Пример задачи — создать тест для `GET /version`, проверяющий статус HTTP 200 и наличие полей `version` и `team` без работающей базы данных:

```powershell
python -m ai.run_crew "Нужен pytest-тест: GET /version возвращает HTTP 200 и JSON с полями version и team. Тест должен работать без запущенной базы данных."
```

Агенты исследуют код бэкенда и записывают результат в `generated/test_version.py`.

Инструмент `write_generated` разрешает создавать и перезаписывать только файлы `generated/test_*.py`. Запись в исходный код бэкенда запрещена. Инструмент `run_linter` проверяет сгенерированный файл через Ruff без автоматических исправлений.

### Проверка сгенерированных тестов

Для запуска тестов из `generated/` установите дополнительные зависимости:

```powershell
python -m pip install -r requirements-generated.txt
```

Затем выполните:

```powershell
python -m pytest generated -q
```

Файл `generated/conftest.py` подготавливает импорт приложения и тестовое значение `DATABASE_URL`, поэтому для проверки `GET /version` не требуется запущенный PostgreSQL.

Обычный запуск:

```powershell
python -m pytest -q
```

использует `pytest.ini` с `testpaths = tests` и запускает основной набор тестов отдельно от `generated/`.

### Трасса и результаты

Трасса первого запуска сохранена в `ai/traces/run-p4-01.log`. Первый запуск потребовал **9 вызовов LLM** и занял **3,0 минуты**.

Сгенерированный тест прошёл pytest, но Кодер не смог самостоятельно исправить ошибку Ruff `I001`: потребовалось ручное применение `ruff --fix`. Этот недостаток зафиксирован в архитектурном решении.

Архитектура описана в `docs/crew-design.md`, принятое решение и результаты эксперимента — в `docs/adr/adr-004-orchestration-pattern.md`.

**Важно:** CrewAI создаёт и проверяет код линтером, но не запускает pytest самостоятельно. Проверку сгенерированного теста выполняет разработчик.
## Генерация тестов с помощью Crew

Для живого запуска нужны работающая Ollama, собранный RAG-индекс
и доступная OpenAPI-схема по адресу, заданному в `AI_BACKEND_URL`.

Посмотреть доступные сценарии:

```powershell
python -m ai
```

Сгенерировать тест для `GET /version`:

```powershell
python -m ai generate-tests "Нужен тест: GET /version отвечает 200, в ответе version и team"
```

Код выхода `0` означает, что итог получен и прошёл проверки контракта.
Код `1` означает отказ или сбой запуска, а `2` — ошибку вызова CLI.

После генерации проверь записанный файл, затем запусти тесты:

```powershell
python -m pytest generated -q
```
